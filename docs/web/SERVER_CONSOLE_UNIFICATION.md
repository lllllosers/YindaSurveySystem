# Yinda Server Console · 统一入口整合

基线：`1255f2c3d7339c46fc786fadde0c1dec9a1b967c`，仍在 `feat/web-server-console-v1-foundation` 开发。不是第二批升级平台，不改 Web 业务或 Desktop，不迁移任何真实业务数据。

## 功能差距与落实

| 原 launcher/core 的实际功能 | 第一批独立 GUI 的缺口 | 本轮统一控制台 |
|---|---|---|
| Web 状态及进程归属 | 已改 SCM，但独立于旧控制台 | 保留；统一查询稳定 Service ID 和注册路径，绝不按端口杀进程 |
| 数据库连接、端口、PG 服务状态 | 依赖 Web 的健康接口，停服时无法独立判断 | 独立数据库连接与迁移检查；可配置 PG 服务名；不把端口打开当作数据库健康 |
| 启动、停止、重启 | 有，但第二套入口 | 原操作名保留，统一走 Windows Service |
| 打开管理端 | 有本机打开 | 保留本机入口；已有 HTTPS 地址可选，恢复可选 HTTPS 检查，不配置公网代理 |
| 正式运行环境预检、迁移 head、页面、可写性、磁盘 | 只有数据库预检 | 恢复完整中文诊断、保存检查结果和分类日志 |
| 立即备份：pg_dump + 全部 storage | 无备份功能，仅预留页面 | 恢复操作和首屏最近备份状态；只有 dump、storage、完成标识齐全才显示完整备份 |
| 开机自启 | 新旧两条路线：计划任务 / Service | 保留设置入口，唯一实现为 SCM 延迟自动启动；不再注册 SYSTEM 最高权限任务 |
| 服务、操作、预检、备份日志分类与尾部读取 | 仅混合读取日志 | 恢复分类与有界尾部读取 |
| 托盘显示、启动停止、退出，关闭时收起 | 缺失 | 恢复，并提供明确“退出控制台（不停止后台服务）” |
| 本机与公网检查 | 内网模式已增加，但旧可选 HTTPS 丢失 | 本机、LAN 候选地址、已有 HTTPS 状态分别展示，不把服务器本机检查当作办公室可达证明 |
| 新部署与已有数据保护 | 新增目录分离和部署状态 | 保留统一配置、持久化目录、部署身份和 Alembic；不自动接管旧数据 |
| 旧便携初始化、停止便携数据库 | 旧专用功能 | 明确退出正式路线；已安装 PG17 独立运行，不在控制台停止 PG 或创建嵌入式集群 |

原 GUI 的运行管理功能得到保留或等价升级。旧便携的环境创建/停止全部是已退役部署方式的专属操作，不适用于正式独立 PostgreSQL，不能作为新正式控制台依赖。其源码、测试和旧交付包保留在 Git 历史，不删除任何磁盘上的旧数据和交付资产。

## 唯一入口和分层

- 唯一正式 GUI 源码入口：`web/launcher.py`，`ServerConsole`。`server_setup.py` 只包含同一程序的安装向导，不是另一个可执行 GUI。
- 唯一正式运维门面：`web/server_console_core.py`，`ServerManager`；GUI 的状态、启停、预检、备份、日志与部署都由此进入。
- `web/deployment/` 是该核心复用的配置、SCM、数据库创建/迁移、诊断适配模块，没有第二套界面或备用进程管理器。
- `server_entry.py` 是非 GUI 的冻结 Web Server/维护命令程序；通过标准输入短暂接收创建管理凭据，不把管理密码放在命令行或配置中。
- 移除 `console_v1.py`、旧松散进程 worker、嵌入式 PG 运行管理和只验证旧机制的测试。保留有价值的行为测试，改为验证 SCM 归属、备份恢复原运行状态等实际合同。
- `build_formal_windows.py` 是唯一正式构建实现；旧 `build_server_console.py` 命令转入同一实现，旧便携构建命令仅给出退役说明。`build_deploy_bundle.py` 只导出源码，不再夹带历史 EXE。`run_dev.bat` 仍是业务开发入口，不是甲方正式控制台。
- 正式包仅有根目录 `引大调查Web中心.exe` 一个 GUI；`service/YindaWebServer/YindaWebServer.exe` 和 WinSW 是后台程序。manifest 记录 GUI 与运维入口，验收同时检查 PE 子系统。旧 `console/` EXE 与 BAT 默认入口已退出本次产品交付。

## 普通用户的首次安装

选择固定程序与数据文件夹 → 选择“为新安装自动创建专用数据库” → 填写 PostgreSQL 安装时的管理密码 → 确认办公室访问地址 → 创建网页登录账号 → 安装并启动后台服务。无需操作 pgAdmin。PostgreSQL 17 本身仍须先安装，向导提供官方安装下载入口。

自动创建仅支持本机并要求显式选择，名称以 `yinda_` 开头；先查询目标库和账号，发现任一同名对象就拒绝，不修改其密码、权限或内容。新账号不是超级用户，没有建库/建角色/复制权限；仅拥有新建的专用数据库。创建进度单独落盘，不存管理凭据。遇到部分创建失败时保留已创建对象与阶段，停止并提示人工核对，不自动 DROP 或改绑空库；当前部署已成功创建的资源仅在 OID/身份匹配时允许继续初始化。

“使用已准备空库”和“接续本控制台已有部署”保留。接续仍需匹配部署身份，旧源码/便携真实数据迁移不在本轮范围。Windows 服务安装仍需要管理员令牌；没有管理员权限不能以进程测试冒充服务验收。

## 备份规则

立即备份先明确提示会短暂停服。仅控制本安装已确认归属的服务；原先运行则先停 Web，再调用同一个后端备份函数转储指定库、复制完整 storage，成功或失败都尝试恢复原有状态。原先停止则保持停止。恢复服务失败单独报告，不能显示全部操作成功。

PostgreSQL 工具从安装注册信息或运行配置所选 bin 定位，不要求甲方配置 PATH；需 PG17 pg_dump。缺失成果目录时拒绝生成“完整备份”。旧版没有完成标识的备份仍可见，但显示“历史备份待核对”，不会当作新完整备份。本轮没有恢复界面、升级平台或定时备份系统。数据库管理密码不进入备份，现有会话和业务数据属于数据库内容，备份目录必须受权限保护。

实际回归、产物和仍待管理员完成的 SCM/注销/重启/LAN 验收记录见 `SERVER_CONSOLE_V1_ACCEPTANCE.md` 的最新整合章节。
