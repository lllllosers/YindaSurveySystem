# Yinda Survey Web Center

`web_center/` 是“引大调查数据采集系统 / YindaSurveySystem”的 Web 业务中心。

当前阶段是 **V1.2.0 中心管理平台**。Web 中心与稳定桌面端使用同一套 `.ydtask V3 / .ydresult 2.2` 业务协议：中央人员在浏览器中管理项目、批次、任务、成果审核和正式成果库，桌面端继续承担离线调查填报。

服务器部署、精简部署包、首次管理员创建和清空测试数据的具体命令见 [DEPLOY.md](DEPLOY.md)。

## Web 与桌面端协同方式

Web 端不是桌面端的重复版本，两端各自承担最适合的工作：

```text
中心建立项目与批次
  ↓
Web 下发任务文件
  ↓
基层桌面端接收任务并离线调查 ─┐
                               ├→ 中心统一审核 → 正式成果库
Web 在线补录与内业填报 ────────┘
  ↓
统一查询、统计和审计
```

这套协同方式带来的直接改善：

- 项目、批次、调查单位和范围只在中心统一确定，桌面端随任务自动带入，减少重复填写；
- 基层现场不依赖网络，继续使用已经稳定的桌面端录入表格和影像；
- 成果上传后自动检查文件完整性、任务范围和数据版本，减少人工逐包核对；
- 多单位成果集中入库，省去反复合并表格、查找最新文件和核对责任单位；
- Web 在线补录和桌面离线调查使用同一任务、同一基础资料和同一正式成果库，不形成两套账；
- 任务、审核、退回和入库均可追溯，便于后续查询、统计和责任确认。

首页主视觉采用原创的庄浪河大渡槽主题图片，用于产品界面展示，不作为工程档案照片或现场影像使用。

## Windows 正式服务控制台

正式部署包中的 `web_center/YindaWebServerConsole.exe` 是服务器运维入口。它管理单个后台 Web 进程，FastAPI 在 `127.0.0.1:8000` 同源提供页面和 API；PostgreSQL 仍由 Windows Service 管理并仅监听本机。控制台不启动 Vite，也不提供生产 `/docs` 入口。

先按 [DEPLOY.md](DEPLOY.md) 配置后端 `.env`、安装 requirements、完成数据库迁移；双击 EXE 后执行“生产环境预检”，再“启动 Web 服务”。窗口关闭会收起到系统托盘，托盘中的“退出控制台”也不会停止 Web；只有“停止 Web 服务”会停服。以管理员身份点击“设置开机自启”，会注册 Windows 任务计划程序 `YindaWebCenter`，开机后后台运行隐藏的 Web 进程。运行日志位于 `web_center/.runtime/logs/`。

`PUBLIC_BASE_URL=https://example.com` 可选，控制台会检查该 HTTPS 地址的 `/api/v1/health`。未配置时显示“未配置公网访问地址”；它不管理或保存隧道服务商凭据。`POSTGRES_SERVICE_NAME` 可选，用来显示 PostgreSQL Windows Service 状态。服务仍必须只监听 `127.0.0.1`，不得将 PostgreSQL 端口暴露公网。

正式成果库保留“导出查询结果”CSV 汇总；每行及详情页的“导出原表”会按同一套桌面表单定义和 `templates/excel` 正式模板生成单条记录的附表 2.1～2.14 Excel 原表。

## 本地开发启动

在仓库根目录双击：

```text
启动Web管理中心.bat
```

该脚本调用 `web_center/run_dev.bat`，迁移开发数据库，然后分别启动带热重载的后端和 Vite 页面。需要后端虚拟环境与前端依赖。它只用于本地开发，服务器部署请使用上面的 EXE。

访问地址：

```text
Web:      http://127.0.0.1:8848
API Docs: http://127.0.0.1:8000/docs
```

使用已有账户登录，也可从登录页提交注册申请。普通申请默认没有登录权限；管理员可在“用户与权限”按待审核状态筛选、多选并批量启用，同时分配查询、审核或管理角色，也可批量清理无效申请。单次批量操作最多处理 200 人，所选账户如有已处理或不存在的申请，整批不会生效。集中注册时，管理员可创建有有效期、人数上限、预设角色及可选管理所范围的邀请口令；使用有效口令注册的账户直接启用，口令仅在创建时完整显示，后续可停用。首次部署仍需使用已有管理员账户或运行管理员创建工具完成初始配置。如果忘记本机 Web 管理员密码，可关闭服务后双击根目录的 `重置Web管理员密码.bat`，按提示输入管理员用户名和新密码；输入过程不会显示密码字符，也不会把明文写入文件。

## 架构边界

### Web 中心负责

- 项目与调查批次管理；
- 用户、角色与权限；
- 操作审计；
- 管理处、管理所、渠系和分管范围新增、修改、停用、启用及安全删除；
- 基础资料内部修订记录，新任务自动携带当时资料的冻结快照；重复保存相同内容不增加修订号；
- 面向管理处或水管所创建调查任务并生成桌面端兼容 `.ydtask V3`；
- 批量登记桌面端已经下发的原始 `.ydtask`，无损接续投产中的历史任务；
- `.ydresult 2.2` 成果包安全接收、SHA-256 留存和文件归档；
- 按 Web 实际下发任务的冻结范围执行来源、组织、渠系、表单和版本冲突预检；
- 桌面成果包单独审核接收/退回、入库前复检和事务化正式入库；
- 附表 2.1～2.14 Web 在线录入、草稿、提交、独立审核队列、退回修改和正式入库；非管理员不能审核本人录入的记录或上传的成果包；
- Web 在线录入照片、视频上传及桌面成果影像统一查看；
- Web 与桌面成果双向查重，避免同一调查对象形成两条正式记录；
- 中央成果库查询、详情、单位分布汇总、CSV 汇总导出与正式 Excel 原表导出。

### PySide6 桌面端继续负责

- 离线调查填报；
- 附表 2.1～2.14 业务表单；
- 本地 SQLite；
- 照片、视频等调查影像；
- 草稿和 completed 调查记录维护；
- 正式原表导出（与 Web 共用模板及渲染定义）；
- `.ydtask` / `.ydresult` 本地包生成与使用。

Web 中心不直接共享或同步桌面端 SQLite。
中央 PostgreSQL 正式成果库是唯一事实源；桌面 SQLite 是离线工作区，任务包和成果包是受控交换载体。

- 面向管理处/水管所生成、下载、取消调查任务；
- 附表 2.1～2.14 在线录入、提交审核、退回修改和正式入库；
- 任务冻结范围、表单版本和任务谱系留存；
- 用户与角色权限管理；
- 注册申请与管理员批量审核启用；首页按角色提示账户申请、桌面成果包和在线记录待办；
- 限时限额注册邀请口令；审核员、只读用户可选择绑定一个管理所范围，服务端限制其任务、成果包、在线记录、正式成果和项目批次读取；未绑定范围的现有用户继续保持原有全局权限；
- 在线调查记录按状态筛选和分页，统计显示全部记录而非当前页数量；在线记录审核有独立页面，与桌面成果包审核分开；
- 在线录入可切换“只看我录入”和全部记录，状态统计随视角同步；草稿内容未变时重复保存不会增加修订号；
- `.ydresult` 上传、结构检查、业务预检、审核、归档、完整性复检与正式入库；
- 成果包按待核验、待审核、待入库、需处理形成工作队列；可多选批量执行业务核验，退回时必须填写原因；
- 已有任务或成果的项目、批次保留历史身份，删除请求给出明确原因，可使用归档或结束状态；
- 未提交在线草稿、未进入审核或入库的成果包、未参与业务的账户可删除；已下发任务和正式成果保留历史关联；
- 正式成果库筛选、详情、来源追溯、单位分布、CSV 汇总导出和单记录 Excel 正式原表导出；
- 审计日志。

首次启用时，系统以 `shared/master_data/official_master_contract.json` 初始化中央基础资料库；此后以 PostgreSQL 中央版本为正式依据。自动测试会检查初始基线与桌面端 V1.2 常量一致。

## `.ydresult` 协议说明

上传阶段先用独立只读检查器执行 ZIP、manifest、文件清单和哈希安全检查；业务预检及正式入库阶段直接调用桌面端 V1.2 的 `survey_result_package_reader`。因此正式协议规则仍以稳定桌面端实现为事实源，Web 不维护第二套业务协议。

Web 入库不会用当前主数据覆盖历史事实。每条正式记录继续保留 `source_task_uid + source_management_scope_uid`；本次向中心提交所依据的任务使用 `submission_task_uid`。处级汇总包可以保留下级真实任务来源，中心按自己下发的处级父任务冻结范围验收。

## 权限边界

当前仅保留已经真实实现的权限：

- `admin`：全部权限；
- `manager`：项目、批次、基础资料、任务下发、在线录入与审核、成果上传/预检/审核/入库、正式成果库和审计；
- `reviewer`：项目、批次、任务读取/下载、成果预检/审核和正式成果库；
- `viewer`：项目、批次、任务、成果与正式成果库只读。

管理员可为 `reviewer` 和 `viewer` 指定一个管理所。受限账户只能查看所属单位相关的项目、批次、任务、成果包、在线记录与正式成果；管理处级汇总任务及成果包仍由全局审核人员处理。`admin` 和 `manager` 始终为全局范围。历史账户默认为全局范围，需要管理员按实际职责逐一分配。

## 安全和部署边界

当前默认配置面向本机 HTTP 开发：

```text
SESSION_COOKIE_SECURE=false
```

正式 HTTPS 部署必须改为：

```text
SESSION_COOKIE_SECURE=true
```

PostgreSQL 不应直接暴露公网。

### 备份与升级

每次正式升级前，在 `web_center/backend` 目录运行：

```bat
.venv\Scripts\python.exe -m app.cli.backup_web_center
.venv\Scripts\alembic.exe upgrade head
```

备份工具生成 PostgreSQL 自定义格式的 `database.dump`、`manifest.json` 和当前 `storage/` 副本，默认放在不进入 Git 的 `backend/backups/时间戳/`。数据库迁移前的快速快照可加 `--database-only`，但它不能替代包含文件的完整备份。请将完整备份复制到独立磁盘并限制访问权限，定期实际演练恢复。恢复时先停止 Web 服务，使用对应版本的数据库和文件备份成套恢复，核对迁移版本与成果文件后再启动；不要将备份目录公开到网页服务器。

当前成果文件使用服务器本地文件系统：

```text
web_center/backend/storage/
```

该目录不进入 Git。

当前部署方案不引入 Redis、Celery、对象存储或微服务。现有正式主数据没有工程坐标，因此页面提供真实的单位/渠道成果分布汇总，不绘制没有数据依据的伪 GIS 地图；后续取得坐标数据后可在中央成果库模型之上增加地图视图。

业务协同细则见 `docs/14_Web与桌面端数据协同规则.md`，本阶段人工验收步骤见 `docs/16_Web基础资料与录入验收说明.md`。
