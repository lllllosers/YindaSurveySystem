# V1.0.2 发布说明

## 版本信息

- 产品名称：引大入秦工程现状调查采集系统
- 版本：V1.0.2
- 阶段：正式版
- 收口日期：2026-09-20
- 升级基线：V1.0.1

## 本次版本重点

V1.0.2 主要解决正式调查开始后暴露出的两类生产问题：

1. 多调查组、多个电脑并行录入时，工程业务编号不能再按“谁先录入谁先编号”处理，而应在汇总后按具体渠道和桩号顺序重新整理；
2. 成果包可能每天累计提交，同一个稳定 UID 的记录会多次出现，需要区分“完全相同、正常更新、旧版本和真正冲突”。

## 工程编号模型

工程对象的跨数据库身份为 `engineering_asset_uid`，调查记录的跨数据库身份为 `survey_record_uid`。

`business_code` 为业务展示编号，不再承担稳定身份职责，也不作为业务 revision 的组成部分。

同一工程在不同汇总阶段可以发生业务编号变化，但 UID 和调查内容身份不变。

## 暂编、重新整理和正式锁号

新建或新导入工程默认处于“暂编”状态。

工程台账提供“整理业务编号”和“锁定正式编号”：

- 整理业务编号：按具体渠系、工程类型和桩号从上游到下游重新生成三位顺序号，可重复执行；
- 锁定正式编号：再次按当前完整数据重新排序后设为“正式”；
- 编号整理与锁号都不会增加业务 revision；
- 正式锁号后如发现漏录，可再次整理，相关工程重新进入暂编，再重新锁号。

## 附表2.1连续性预检

正式锁号前：

- 终点桩号不大于起点桩号：阻断；
- 同一具体渠道渠段重叠：阻断；
- 两渠段存在间隔：提示人工核验，确认没有漏录后允许继续；
- 单个调查渠段超过 3000 m：提示核验，不直接阻断；
- 当前批次存在未完成/草稿工程记录：阻断。

渠段间隔可能由隧洞、渡槽、倒虹吸、其他建筑物、未衬砌段或管理边界造成，因此不机械要求所有相邻渠段首尾完全相等。

## 增量成果回收

`.ydresult` 当前 schema 为 `2.2`。

接收端按稳定 UID、revision 和业务内容识别新增、已存在且一致、待更新、旧版本和冲突。

同一记录累计提交时：

- 内容和版本相同：跳过；
- 下级有新的合法业务修订：提示待更新，经确认后合并；
- 旧版本成果：不覆盖新版本；
- 双方均发生不一致修改：按冲突处理；
- 只有业务编号不同：不视为业务内容更新或冲突。

接收端已有工程的本地业务编号不会被下级成果包中的临时编号覆盖。

## 当前三级业务流转方式

V1.0.2 尚未实现软件内部原生的“中心 → 处 → 所”父子任务链。

当前可采用以下中继方式：

```text
中心
  ├─ 在一套全新 local_data 中建立项目/批次
  ├─ 生成全部水管所 .ydtask
  └─ 保留完整 local_data 和任务下发历史
       │
       └─ 将软件副本 + 该 local_data + 所级任务包整体交给处
                    │
                    ├─ 处把对应 .ydtask 分给各所
                    ├─ 各所使用全新 local_data 接收自己的任务
                    ├─ 各所录入并导出 .ydresult
                    └─ 处使用中心复制下来的 local_data 接收各所成果
                              │
                              ├─ 审查
                              ├─ 汇总
                              ├─ 重新整理编号
                              ├─ 锁定正式编号
                              └─ 再导出 .ydresult 返回中心
                                           │
                                           └─ 中心最终接收汇总成果
```

这一方式能成立的关键是：处使用的是中心生成全部所级任务包之后复制出的同源 `local_data`，因此处和中心都保存相同的 issued-task / issued-scope 冻结历史；成果记录中的 `source_task_uid + source_management_scope_uid` 继续保留。

### 当前操作边界

1. 中心应先生成本轮需要的全部所级任务包，再把 `local_data` 副本交给处；
2. 处开始接收所级成果后，不要再用中心新的 `local_data` 直接覆盖处数据库；
3. 处和中心之间后续只通过 `.ydresult` 传递成果，不直接合并 SQLite 数据库；
4. 各所必须使用各自独立、全新的 `local_data` 接收任务；
5. 处汇总多个所成果后，应以处当前完整数据重新整理编号；最终锁号应在数据相对完整的汇总层执行；
6. 如果中心后续又新生成了此前处副本中不存在的任务，处端不会自动拥有该任务的 issued-task 历史，本轮应避免在处开始汇总后再追加这种任务。

该方式属于 V1.0.2 的临时生产组织方案，不等同于系统已经实现真正的三级任务分发。

## UI 修复

本版本同时修复：

- 点击“调查录入”时主窗口被隐藏表单尺寸建议横向撑宽；
- 限制窗口自动增宽后，工程调查列表筛选控件在默认窗口宽度下发生重叠；
- 工程调查列表改为两行网格筛选布局；
- 正式锁号的间隔、重叠、超长等提示改为面向实际业务人员的中文说明。

## 数据兼容和升级

V1.0.2 启动现有 V1.0.1 数据库时自动执行幂等 schema migration。

主要变化包括：

- EngineeringAsset 增加 revision/source revision/code status；
- SurveyRecord 增加 revision/source revision；
- 移除旧的项目级 `UNIQUE(project_id, business_code)`；
- 正式业务编号唯一范围调整到具体渠道；
- 既有稳定 UID 和调查内容保持。

升级前建议独立备份原 `local_data`。

## 发布验证

V1.0.2 已完成全量自动化回归、增量成果合并、同 UID 不同编号、不同具体渠道同号、可重复编号、正式锁号、附表2.1连续性检查以及调查录入 UI 稳定性验证。

## 未改变的业务边界

- 附表1.1～1.15仍不启用桌面软件化录入；
- `.ydtask` 任务包协议保持现有模型；
- 真正的中心→处→所三级任务链尚未实现；
- Web Hybrid / Web Center 实验能力不进入桌面 V1.0.2 正式包；
- V1.0.0、V1.0.1 标签和既有正式发布包保持冻结，不重写、不覆盖。
