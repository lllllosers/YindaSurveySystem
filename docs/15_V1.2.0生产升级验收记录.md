## V1.1.1 → V1.2.0 隔离升级模拟

升级模拟没有使用当前代码人工伪造“旧数据库”，而是：

1. 从正式 `v1.1.1` Tag 建立临时 Git worktree；
2. 使用 V1.1.1 的真实数据库代码创建旧版本 SQLite 数据库；
3. 为11张原 point 附表分别建立一条 V1、completed、单桩号历史记录；
4. 给记录和工程对象设置独立 revision、source_revision 和固定 updated_at；
5. 将旧数据库复制到隔离升级目录；
6. 使用当前 `release/v1.2.0` 完整 application bootstrap 执行升级；
7. 校验升级前备份、迁移结果和第二次启动幂等性；
8. 临时环境自动清理，不接触开发机正式 `local_data`。

## 升级前备份验收

既有 V1.1.1 数据库首次由 V1.2.0 application bootstrap 打开时，自动生成：

```text
local_data/backups/yinda_survey_<时间>_pre_v1_2_0_upgrade.db
```

并通过 SQLite `PRAGMA quick_check`。

对该备份读取确认：其中仍是迁移前的 V1.1.1 单桩号状态，因此备份时点位于 V1.2.0 数据迁移之前。

全新数据库不会生成空的 `pre_v1_2_0_upgrade` 备份。

## 数据兼容结论

V1.2.0 不要求甲方重建既有数据库。

历史单桩号数据采用“保留原值、补起始桩号、不猜终止桩号”的兼容策略；需要补充的终止桩号由业务人员依据档案或现场事实补录。

历史 completed 记录不因升级自动退回 draft。

本次迁移不被视为业务编辑，不主动改变业务 revision、来源 revision 和更新时间。
