# Web 与桌面端数据协同规则

## 一、唯一正式依据

系统只保留一个事实源：Web 中心使用的 PostgreSQL 中央数据库。Web 页面和桌面端不是两套互相覆盖的数据库。

- 基础资料由 Web 中心统一维护并生成版本。
- Web 在线录入和桌面成果都必须经过中心审核，审核通过后进入同一正式成果库。
- 桌面端保留离线工作数据和已接收任务快照，但它们在回传审核前不属于中心正式成果。

## 二、基础资料如何同步

1. 管理处、管理所、渠道和分管范围只在 Web 中心维护。
2. 每次新增、修改、停用、启用或删除都会生成新的中心资料版本。
3. 中心创建桌面调查任务时，把当时版本的资料快照写入 `.ydtask` 任务包。
4. 桌面端导入任务后按快照离线工作；已经下发的任务不跟随后台修改，保证历史口径可追溯。
5. 基础资料发生调整并且现场需要使用新口径时，应由中心重新下发任务，不允许桌面端自行修改正式资料。

使用中的资料不能直接删除。存在下级资料、调查任务、在线记录或正式成果时，只允许停用；停用资料不再进入新任务和新录入，但历史数据继续正常显示。

## 三、调查数据如何协同

### 桌面端录入

中心下发任务包 → 桌面端导入并离线调查 → 桌面端导出 `.ydresult` 成果 → Web 中心上传、预检、审核 → 进入正式成果库。

### Web 端录入

选择中心已有任务和分管范围 → 在线填写草稿 → 提交审核 → 审核通过 → 直接进入同一个正式成果库。

Web 记录不需要复制到每台桌面电脑。桌面端只有在承担离线现场任务时才接收任务快照；正式成果的查询、统计和版本判断一律以中心库为准。

## 四、避免两套事实的规则

- 草稿不是正式数据；只有中心审核入库的记录才是正式数据。
- 同一项目、工程类型、管理单位、渠道和调查对象名称出现重复时，系统阻止第二条记录进入审核或入库。
- 同一正式记录再次提交时，必须使用相同的稳定编号和更高的修订号；旧版本不能覆盖新版本，同一版本内容不同会被判为冲突。
- 桌面成果在上传时再次按任务范围、资料快照、表单版本和记录来源进行预检。
- Web 已提交但尚未审核的记录，也会参与桌面成果查重，避免两边同时建档。
- 审核、入库、基础资料调整均记录操作人和时间，便于追溯。

## 五、断网和失败处理

- 桌面端可离线工作；网络恢复后通过成果文件回传，不要求两端实时在线。
- Web 草稿保存在中心库，可退出后继续填写。
- 上传、预检或审核失败时，不会产生半条正式记录；处理问题后重新操作即可。
- 中心数据库必须纳入定期备份。任务包和成果包是交换与审计载体，不替代数据库备份。

## 六、职责边界

| 内容 | 正式维护位置 | 桌面端作用 | Web 端作用 |
| --- | --- | --- | --- |
| 基础资料 | 中心数据库 | 随任务读取冻结快照 | 维护、版本化、下发 |
| 调查任务 | 中心数据库 | 接收并执行 | 建立、下发、跟踪 |
| 现场离线记录 | 桌面本地工作区 | 采集、校验、导出 | 上传后预检审核 |
| 在线补录记录 | 中心数据库 | 不做重复副本 | 填写、提交、审核 |
| 正式调查成果 | 中心数据库 | 通过成果包提交修订 | 唯一查询、汇总和审计入口 |

## 七、当前人工验收重点

1. 修改基础资料后确认中心版本号增加；旧任务详情中的资料版本不变，新任务使用新版本。
2. 为同一渠道建立相邻分段（例如 `0+000—10+000`、`10+000—20+000`）应成功；建立重叠分段应被阻止。
3. 有下级或业务引用的资料应无法删除；停用后不再出现在新任务和新录入选择中。
4. Web 提交一条记录后，再用桌面端提交同名同范围记录，应在预检阶段收到重复提醒。
5. 桌面成果入库后，再从 Web 提交同名同范围记录，应在提交阶段收到重复提醒。
