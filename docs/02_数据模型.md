# 引大灌区调查数据采集系统
## V0.2 数据模型确认稿

> 文档版本：V0.2  
> 当前阶段：概念数据模型确认  
> 状态：经讨论确认  
> 原则：先保证长期可用、历史可追溯和后续可扩展，再进入 SQLite 物理表设计与代码实现

---

## 1. 数据模型设计目标

本系统不是一次性填表工具，而是面向多批次、可重复调查的本地化调查数据管理系统。

系统需要同时支持：

1. 本轮调查从零开始建立调查数据；
2. 第一次调查过程中逐步建立工程对象台账；
3. 同一工程对象以后能够参加多次调查；
4. 不同调查批次的数据相互独立；
5. 历史调查数据不得被新调查覆盖；
6. 调查表未来允许产生新版本；
7. 不同版本调查表允许拥有不同字段和评价标准；
8. 附表 1 和附表 2 使用统一的调查批次体系；
9. Excel 只作为成果输出和未来导入接口，不作为核心数据库；
10. 当前未明确的照片、坐标、综合判级等需求保留扩展口，不提前复杂开发。

# 2. 总体数据关系

系统核心关系如下：

```text
项目 Project
│
├── 调查批次 SurveyBatch
│     │
│     ├── 附表1综合调查记录
│     └── 附表2工程调查记录
│
├── 组织机构 OrganizationUnit
│
├── 渠系 CanalUnit
│
├── 工程对象 EngineeringAsset
│     │
│     ├── 2026调查记录
│     ├── 2027调查记录
│     └── 后续调查记录
│
└── 调查表定义 FormDefinition
      │
      ├── V1 / 2026版
      ├── V2 / 后续版本
      └── ...
```

核心原则：

**工程对象是长期存在的实体，调查记录是某一次调查产生的数据。**

## 3.1 含义

Project 表示一套长期管理的调查项目。

当前项目：

```text
引大入秦灌区现状调查
```

当前阶段通常只有一个项目，但数据模型保留多项目能力。

## 3.2 主要属性

建议包括：

- 内部 ID
- 项目名称
- 项目简称
- 项目说明
- 创建时间
- 项目状态

# 4. SurveyBatch：调查批次

## 4.1 含义

SurveyBatch 表示一次独立的调查活动。

例如：

```text
2026年度全面调查
2027年度调查
2027年专项调查
```

## 4.2 主要属性

建议包括：

- 内部 ID
- 所属项目 ID
- 批次名称
- 批次代码
- 开始日期
- 结束日期
- 调查说明
- 状态
- 创建时间

状态可暂定：

```text
draft       草稿
active      正在调查
completed   已完成
archived    已归档
```

## 4.3 核心规则

新建调查批次时：

- 不覆盖旧批次；
- 可以引用以前已经建立的工程对象；
- 可以复制允许沿用的历史字段；
- 复制后的数据属于新批次，可以独立修改。

例如：

```text
2026调查记录
      ↓ 复制允许沿用内容
2027调查记录
```

而不是：

```text
2027直接修改2026数据
```

# 5. OrganizationUnit：组织机构

## 5.1 含义

用于保存调查业务中的组织和管理层级。

V0.1 主要表现为：

```text
基层处
└── 水管所
```

## 5.2 底层采用树形结构

数据库中只建立一张组织机构表，通过：

```text
parent_id
unit_type
```

表示上下级关系。

示例：

```text
总干渠处
├── 01 A水管所
├── 02 B水管所
└── 03 C水管所
```

数据示意：

| id | 名称 | 类型 | parent_id | 业务代码 | 状态 |
|---|---|---|---|---|---|
| 1 | 总干渠处 | department | NULL | 1 | active |
| 2 | A水管所 | water_office | 1 | 01 | active |

## 5.3 V0.1 UI 范围

虽然底层支持树形结构，但 V0.1 界面只开放：

```text
基层处
↓
水管所
```

不开发复杂组织树设计器。

## 5.4 历史处理

已经产生历史调查数据的组织机构原则上不物理删除，只能：

```text
停用
```

普通录入错误可以纠正名称。

真实组织撤并或身份变化时，优先采用：

```text
停用旧机构
+
新建新机构
```

# 6. CanalUnit：渠系

## 6.1 含义

用于保存渠道及其上下级关系。

例如：

```text
干渠
└── 分干渠
    └── 支渠
        └── 分支渠
```

## 6.2 渠道层级

当前编号规则中的渠道层级包括：

```text
01 干渠
02 分干渠
03 支渠
04 分支渠
```

## 6.3 主要属性

建议包括：

- 内部 ID
- 渠道名称
- 渠道层级
- 上级渠道 ID
- 所属组织机构 ID
- 渠道代码
- 状态
- 备注

## 6.4 底层采用树形结构

通过：

```text
parent_id
```

表示上级渠道。

## 6.5 与组织机构的关系

组织机构和渠系必须是两套独立结构。

不采用：

```text
基层处
└── 水管所
    └── 干渠
        └── 支渠
```

这种混合树。

正确关系为：

```text
组织机构树
基层处
└── 水管所
```

和：

```text
渠系树
干渠
└── 分干渠
    └── 支渠
```

二者通过关联字段建立管理关系。

## 6.6 历史处理

已经被历史调查使用的渠系原则上不物理删除，只能停用。

# 7. 渠道层级代码与具体渠系 ID 分离

当前业务编号中的渠道部分表示的是：

```text
渠道层级
```

而不是某条具体渠道的唯一编号。

例如：

```text
01 = 干渠
03 = 支渠
```

因此系统必须区分：

```text
CanalUnit 内部 ID
```

和：

```text
渠道层级业务代码
```

例如：

```text
CanalUnit ID：127
渠道名称：东一干渠
渠道层级：干渠
渠道层级代码：01
```

业务编号生成时使用渠道层级代码。

数据查询和对象归属时使用 CanalUnit 内部 ID。

# 8. EngineeringAsset：工程对象

## 8.1 含义

EngineeringAsset 表示现实世界中长期存在的一处工程实体或一个工程调查单元。

例如：

```text
K0+000～K2+850 防渗衬砌渠道
1号节制闸
某渡槽
某倒虹吸
某隧洞
某涵洞
某桥梁
```

## 8.2 第一次调查逻辑

当前没有完整工程基础台账。

第一次调查时：

```text
录入附表2
      ↓
发现/登记工程
      ↓
创建 EngineeringAsset
      ↓
同时创建本批次 SurveyRecord
```

也就是说：

```text
第一次调查
=
建立工程台账
+
填写本次调查结果
```

以后再次调查：

```text
从 EngineeringAsset 中选择已有工程
      ↓
创建新的 SurveyRecord
```

## 8.3 工程对象只保存长期身份信息

EngineeringAsset 主要保存：

- 内部 ID
- 工程名称
- 工程类别
- 所属组织机构 ID
- 所属渠系 ID
- 业务编号
- 编号规则版本
- 起始桩号（如适用）
- 终止桩号（如适用）
- 单点桩号（如适用）
- 首次登记批次
- 当前状态
- 创建时间
- 备注

## 8.4 不把易变化的工程参数固定到工程对象中

例如以下信息虽然看似属于“基础数据”，但未来可能因改造而变化：

```text
设计流量
结构形式
加固改造年月
混凝土强度
尺寸参数
```

这些具体调查参数原则上仍保存在每一次 SurveyRecord 中。

这样可以保留：

```text
2026调查参数
2027调查参数
2028调查参数
```

的历史变化。

# 12. FormVersion：调查表版本

## 12.1 含义

同一张调查表未来允许发生修改。

例如：

```text
附表2.2
├── V1 / 2026版
└── V2 / 后续版本
```

## 12.2 核心规则

已经被正式调查记录使用的 FormVersion 不直接修改。

如果字段、结构或评价标准发生实质变化：

```text
复制旧版本
↓
创建新版本
↓
修改新版本
```

历史数据继续绑定旧版本。

## 12.3 schema_json

FormVersion 中保存：

```text
schema_json
```

用于完整保存该版本调查表结构快照。

其中包括：

- 普通字段；
- 字段代码；
- 中文名称；
- 数据类型；
- 单位；
- 是否必填；
- 默认值；
- 是否允许沿用上期数据；
- UI 控件类型；
- 分组信息；
- 矩阵信息；
- 重复行信息；
- 评价项目；
- A/B/C/D 标准；
- 排序；
- 备注等。

## 12.4 配置与数据库快照

项目代码中的：

```text
config/forms/
```

用于保存开发期表单配置。

软件初始化时，将配置写入：

```text
FormVersion.schema_json
```

历史记录以后以数据库中保存的 schema_json 快照为准。

不能用新版配置自动解释和覆盖旧版调查记录。

```text

```

```json
{
  "name": "1号节制闸",
  "stake": "K12+350",
  "design_flow": 4.5,
```

# 16. 为什么不为 29 张调查表建立 29 张固定 SQLite 表

不采用：

```text
form_1_1
form_1_2
...
form_2_14
```

这种固定物理表结构。

原因：

1. 调查表未来可能修改；
2. 不同年度版本字段可能不同；
3. 每次修改数据库列会增加迁移成本；
4. 历史数据解释容易受新版本影响；
5. 附表1存在矩阵和重复行，不适合全部硬编码成列。

---

# 17. 为什么不采用完全 EAV 动态字段模式

也不采用：

```text
FieldDefinition
RecordFieldValue
```

将每一个单元格都保存成独立数据库行。

原因：

1. 对本地单用户系统过度复杂；
2. 查询和导出时需要频繁行列转换；
3. 调试成本高；
4. 数据库会产生大量碎片化记录；
5. JSON 已足够满足当前调查表版本变化需求。

因此采用：

**核心关系型字段 + record_data_json + InspectionResult**

的混合模式。

# 18. InspectionResult：附表2分项评价结果

附表2中的 a/b/c/d 或 a/b/c 分项评价不全部塞入 record_data_json。

单独使用：

```text
InspectionResult
```

保存。

主要属性建议包括：

- 内部 ID
- SurveyRecord ID
- 检查项目代码
- 检查大类
- 检查项目名称
- 评价等级
- 情况描述
- 备注
- 修改时间

这样便于以后：

- 查全部 C 类检查项目；
- 查全部 D 类问题；
- 按工程类型统计分项评价；
- 导出问题清单；
- 做质量核验。

# 19. 评价标准与现场情况描述分离

必须严格区分：

```text
评价标准
```

和：

```text
现场情况描述
```

评价标准来自 FormVersion.schema_json。

现场情况描述来自实际纸质调查结果录入。

二者不得混为一个字段。

# 22. 附表1内部数据结构

附表1虽然都属于综合调查，但内部大致存在三类数据结构。

## 22.1 field：普通字段型

适用于：

```text
一个调查项目
→ 一个值
```

例如：

```text
总人口
农业人口
年平均气温
设计灌溉面积
执行水价
```

在 schema_json 中作为：

```text
field
```

处理。

---

## 22.2 matrix：矩阵型

适用于：

```text
指标 × 分类
```

例如：

```text
作物 × 指标
水源 × 年份
用途 × 年份
```

在 schema_json 中作为：

```text
matrix
```

处理。

record_data_json 示例：

```json
{
  "crop_system": {
    "wheat": {
      "area": 10.5,
      "planting_ratio": 22.4,

      "area": 25.8,
      "planting_ratio": 55.1,
      "annual_water_use": 780
    }
  }
}
```

---

## 22.3 repeater：重复行型

适用于：

```text

→ 每一行包含一组属性
```

例如：

```text

多类排水工程
规划工程项目
```

在 schema_json 中作为：

```text
repeater
```

处理。

record_data_json 示例：

```json
{

    {
      "name": "A",
      "structure_type": "泵站",
      "design_supply": 123.4
    },
    {
      "name": "B",
      "structure_type": "水库",
      "design_supply": 456.7
    }
  ]
}
```

# 24. 附表1中的工程条目暂不自动创建 EngineeringAsset

附表1中部分表格存在工程条目，但当前不能确认这些条目是否与附表2工程对象严格一一对应。

因此：

```text
附表1中的工程条目
≠
自动创建 EngineeringAsset
```

第一版仅作为附表1调查结果保存。

以后如果甲方明确需要关联，再增加：

```text
关联已有工程对象
```

能力。

# 25. 附表1与附表2的数据关系

附表1和附表2的原始调查结果保持独立。

未来可以：

```text
附表1综合数据
↔
附表2工程明细数据
```

进行一致性核验。

例如：

```text
附表1记录水闸数量 = 50
附表2实际水闸记录 = 48
```

系统未来可以提示差异。

但不能自动用附表2结果覆盖附表1原始调查值，除非甲方未来明确确定自动汇总口径。

---

# 26. 业务编号

业务编号与数据库内部 ID 完全分开。

例如：

```text
数据库内部 ID：
84217

业务编号：
1-01-01-02-037
```

数据库内部 ID：

- 系统内部使用；
- 永久稳定；
- 用户通常不可见。

业务编号：

- 面向调查业务；
- 可以自动生成；
- 可以查询；
- 未来规则允许调整。

# 27. 当前业务编号组成

当前附表2编号按：

```text
基层处代码
-
水管所代码
-
渠道层级代码
-
附表/工程类型代码
-
顺序号
```

例如：

```text
1-01-01-02-037
```

系统应支持：

```text
选择基层处
      ↓
选择水管所
      ↓
选择具体渠系
      ↓
自动识别渠道层级
      ↓
根据当前调查表识别工程类型
      ↓
自动建议顺序号
      ↓
生成业务编号
```

正常情况下不要求用户重复手工选择渠道层级。

渠道层级由具体渠系自动推断。

# 31. 调查记录状态

SurveyRecord 状态采用：

```text
draft       草稿
completed   录入完成
void        已作废
```

注意：

```text
completed
```

仅表示：

**内业录入完成**

不代表：

- 水管所负责人审核通过；
- 工程科审核通过；
- 基层处正式审核通过；
- 纸质签字程序完成。

---

# 32. 草稿记录

草稿记录：

- 允许未填写完整；
- 允许未完成评价；
- 允许继续修改；
- 允许直接删除；
- 不需要生成大量历史修改版本。

---

# 33. 录入完成记录

录入完成的记录：

- 原则上不物理删除；
- 如需废弃，改为已作废；
- 再次修改时应保留修改前历史快照。

---

# 34. 已作废记录

已作废记录：

- 不再作为有效调查成果；
- 仍保留在数据库；
- 查询时默认隐藏；
- 可选择查看历史；
- 可记录作废原因。

作废原因可包括：

```text
重复录入
纸质原表作废
工程对象对应错误
其他
```

---

# 35. RecordRevision：调查记录历史修订

增加：

```text
RecordRevision
```

用于保存已完成记录修改前的历史快照。

主要属性建议包括：

- revision_id
- survey_record_id
- revision_no
- data_snapshot_json
- inspection_snapshot_json
- overall_grade
- record_status
- created_at
- reason

V0.1 不做复杂逐字段审计界面。

---

# 36. 修改历史原则

草稿阶段：

```text
直接覆盖保存
```

不每次生成 revision。

录入完成以后：

```text
修改并保存
      ↓
先保存旧版本快照
      ↓
再写入新值
```

这样避免自动保存产生大量无意义版本。

---

# 37. 修改人

V0.1 为单用户系统，不开发登录和权限体系。

历史记录第一版可只保存：

```text
修改时间
```

`modified_by` 可预留为空字段。

以后多人系统再启用。

---

# 38. 调查记录不能跨批次直接迁移

一条属于：

```text
2026年度调查
```

的 SurveyRecord 不允许直接修改为：

```text
2027年度调查
```

如果录错批次：

- 草稿：删除后在正确批次重新创建；
- 已完成：作废原记录，再在正确批次创建新记录。

调查批次是历史定位的一部分。

---

# 39. EngineeringAsset 可被多个调查批次复用

例如：

```text
工程对象：1号节制闸
```

下面可以存在：

```text
2026 SurveyRecord
2027 SurveyRecord
2028 SurveyRecord
```

工程对象长期存在。

调查记录分别属于自己的调查批次。

---

# 40. 数据继承原则

未来新建调查批次时，部分字段可以沿用上一次调查值。

系统采用：

```text
复制值
```

而不是：

```text
共享旧值
```

例如：

```text
2026设计流量 = 4.5
```

新建 2027 调查：

```text
复制 → 2027设计流量 = 4.5
```

以后 2027 修改为：

```text
4.8
```

不会影响 2026 历史记录。

---

# 41. FormVersion 冻结原则

已经被正式调查记录引用的 FormVersion 视为冻结。

不能直接覆盖修改：

```text
schema_json
```

未来调查表变化时：

```text
复制旧版本
↓
创建新版本
↓
修改新版本
```

历史调查记录继续使用旧版 schema_json。

且：

的数据。

工作数据导出可提供：

```text
包含草稿
```

选项。

已作废记录默认不进入正式成果。

# 49. 不可违反的数据规则

系统后续开发必须遵守：

1. 历史调查记录不得被新批次覆盖；
2. 工程对象与调查记录必须分离；
3. 数据库内部 ID 与业务编号必须分离；
4. 组织机构与渠系必须分离；
5. 渠道层级代码与具体渠系 ID 必须分离；
6. 已使用的调查表版本不得直接覆盖修改；
7. 评价标准与现场情况描述必须分离；
8. 综合 a/b/c/d 判级算法必须独立；
9. 附表1与附表2原始调查结果保持独立；
10. Excel 只是输入输出接口，不作为核心数据库；
11. 真实调查数据不得写入程序代码或 Git 仓库；
12. 新批次继承历史数据时必须复制，而不是共享同一值；
13. 已完成记录修改时必须保留旧版本快照；
14. 已完成记录原则上不物理删除，采用作废；
15. 当前不确定的业务规则优先预留，不提前写死。
