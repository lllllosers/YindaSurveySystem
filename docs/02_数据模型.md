# 引大灌区调查数据采集系统
## V0.1 数据模型设计

> 文档版本：V0.1  
> 当前阶段：概念数据模型设计  
> 原则：先确定业务对象及关系，再设计 SQLite 物理表结构

---

## 1. 数据模型设计目标

本系统不是一次性填表工具。

系统需要同时支持：

1. 本轮调查从零开始建立调查数据；
2. 第一次调查过程中逐步建立工程对象台账；
3. 同一工程对象以后能够参加多次调查；
4. 不同调查批次的数据相互独立；
5. 历史调查数据不得被新调查覆盖；
6. 调查表未来允许产生新版本；
7. 不同版本调查表允许拥有不同字段和评价标准；
8. 附表 1 和附表 2 使用统一的调查批次管理；
9. Excel 只是成果输出形式，不作为核心数据库。

---

## 2. 总体数据关系

系统核心关系如下：

```text
项目 Project
│
├── 调查批次 SurveyBatch
│     │
│     ├── 附表1综合调查记录
│     │
│     └── 附表2工程调查记录
│
├── 组织机构 OrganizationUnit
│
├── 渠系 CanalUnit
│
├── 工程对象 EngineeringAsset
│     │
│     ├── 2026调查记录
│     ├── 2027调查记录
│     └── 后续调查记录
│
└── 调查表定义 FormDefinition
      │
      ├── V1 / 2026版
      ├── V2 / 后续版本
      └── ...
```

核心原则：

**工程对象是长期存在的实体，调查记录是某一次调查产生的数据。**

## 3. Project：调查项目

### 3.1 含义

Project 表示一套长期管理的调查项目。

当前项目：

```text
引大入秦灌区现状调查
```

当前阶段通常只有一个项目，但数据模型保留多个项目的能力。

### 3.2 主要属性

建议包括：

- 内部 ID
- 项目名称
- 项目简称
- 项目说明
- 创建时间
- 项目状态

示例：

```text
Project
ID: 1
名称: 引大入秦灌区现状调查
状态: active
```

---

## 4. SurveyBatch：调查批次

### 4.1 含义

SurveyBatch 表示一次独立的调查活动。

例如：

```text
2026年度全面调查
2027年度调查
2027年专项调查
```

### 4.2 主要属性

建议包括：

- 内部 ID
- 所属项目 ID
- 批次名称
- 批次代码
- 开始日期
- 结束日期
- 调查说明
- 状态
- 创建时间

状态可暂定：

```text
draft       草稿
active      正在调查
completed   已完成
archived    已归档
```

### 4.3 核心规则

新建调查批次时：

- 不覆盖旧批次；
- 可以引用以前已经建立的工程对象；
- 可以复制允许沿用的历史字段；
- 复制后的数据属于新批次，可以独立修改。

即：

```text
2026调查记录
      ↓ 可选择复制
2027调查记录
```

而不是：

```text
2027直接修改2026数据
```

## 5. OrganizationUnit：组织机构

### 5.1 含义

用于保存调查工作中的组织和管理层级。

例如：

```text
基层处
└── 水管所
```

当前已知基层处包括：

- 总干渠处
- 东一干灌区处
- 东二干灌区处
- 兰州新区供水处
- 白银供水处

水管所实际名单可在正式调查过程中逐步建立。

### 5.2 采用树形结构

OrganizationUnit 不分别建立：

```text
处表
水管所表
```

而采用一张组织机构表，通过 parent_id 表示上下级。

例如：

```text
总干渠处
├── A水管所
├── B水管所
└── C水管所
```

数据示意：

| id | 名称 | 类型 | parent_id | 业务代码 |
|---|---|---|---|---|
| 1 | 总干渠处 | department | NULL | 1 |
| 2 | A水管所 | office | 1 | 01 |
| 3 | B水管所 | office | 1 | 02 |

### 5.3 优点

如果以后增加：

```text
管理站
班组
其他管理机构
```

不需要重新设计数据库。

## 6. CanalUnit：渠系

### 6.1 含义

保存渠道及其上下级关系。

例如：

```text
总干渠
└── 某分干渠
    └── 某支渠
        └── 某分支渠
```

### 6.2 渠道层级

当前编号规则中的渠道层级包括：

```text
01 干渠
02 分干渠
03 支渠
04 分支渠
```

### 6.3 主要属性

建议包括：

- 内部 ID
- 渠道名称
- 渠道层级
- 上级渠道 ID
- 所属组织机构 ID
- 渠道代码
- 备注
- 状态

### 6.4 采用树形结构

与组织机构类似：

```text
parent_id
```

表示上级渠道。

这样以后可以形成：

```text
干渠
→ 分干渠
→ 支渠
→ 分支渠
```

## 7. EngineeringAsset：工程对象

### 7.1 含义

EngineeringAsset 表示现实世界中长期存在的一处工程实体或一个工程调查单元。

例如：

```text
K0+000～K2+850 防渗衬砌渠道
1号节制闸
某渡槽
某倒虹吸
某隧洞
某涵洞
某桥梁
```

### 7.2 第一次调查的特殊逻辑

当前没有完整工程基础台账。

因此第一次调查采用：

```text
录入附表2
      ↓
发现/登记工程
      ↓
创建 EngineeringAsset
      ↓
同时创建本批次 SurveyRecord
```

也就是说：

第一次调查同时完成：

```text
建立工程台账
+
填写2026调查结果
```

以后再次调查：

```text
从 EngineeringAsset 中选择已有工程
      ↓
创建新的调查记录
```

### 7.3 主要属性

工程对象中只保存长期身份信息和定位关系。

建议包括：

- 内部 ID
- 工程名称
- 工程类别
- 所属组织机构 ID
- 所属渠系 ID
- 业务编号
- 编号规则版本
- 起始桩号（如适用）
- 终止桩号（如适用）
- 单点桩号（如适用）
- 首次登记批次
- 当前状态
- 创建时间
- 备注

### 7.4 注意

以下内容原则上不能仅存在 EngineeringAsset 中：

```text
当前破损程度
当前评价等级
本次水流情况
本次裂缝情况
本次调查描述
```

因为这些内容会随调查时间变化。

它们属于 SurveyRecord。

## 8. 桩号数据

为方便以后排序、区间查询和 GIS 扩展，桩号不能只保存显示文本。

例如：

```text
K12+350
```

建议同时具有：

```text
显示值：K12+350
标准数值：12350 m
```

渠段则保存：

```text
起始桩号数值
终止桩号数值
```

UI 可以继续向用户显示：

```text
K12+350
```

数据库内部使用数值参与：

- 上下游排序；
- 范围查询；
- 渠段长度检查；
- 重叠检查。

## 10. FormVersion：调查表版本

### 10.1 含义

同一张调查表未来允许发生修改。

例如：

```text
附表2.2
├── V1 / 2026版
└── V2 / 2027版
```

### 10.2 核心规则

```text

```

### 10.3 主要属性

建议包括：

- 内部 ID
- FormDefinition ID
- 版本号
- 版本名称
- 生效时间
- 是否当前版本
- 创建时间
- 备注

## 13. SurveyRecord：调查记录

### 13.1 含义

SurveyRecord 是系统最核心的数据之一。

表示：

**某个调查批次中，某个调查对象填写的一张调查表。**

例如：

```text
2026年度全面调查
+
1号节制闸
+
附表2.2 V1
=
一条 SurveyRecord
```

### 13.2 主要属性

建议包括：

- 内部 ID
- Project ID
- SurveyBatch ID
- FormVersion ID
- 调查记录类型
- 所属组织机构 ID
- 所属渠系 ID
- EngineeringAsset ID（附表2时使用）
- 调查日期
- 最终工程类别
- 调查意见与建议
- 记录状态
- 创建时间
- 修改时间

### 13.3 调查记录类型

暂定：

```text
comprehensive   附表1综合调查
engineering     附表2工程调查
```

### 13.4 附表1记录

附表1通常没有 EngineeringAsset。

主要绑定：

```text
调查批次
+
调查表版本
+
组织机构
+

```

例如：

```text
2026年度调查
+
附表1.2
+
某水管所
+
某支渠
```

### 13.5 附表2记录

附表2主要绑定：

```text

+

+

```

## 14. RecordFieldValue：普通字段实际值

FieldDefinition 描述“应该填什么”。

RecordFieldValue 保存“实际填了什么”。

例如：

```text
FieldDefinition:
设计流量

RecordFieldValue:
4.5
```

关系：

```text
SurveyRecord
      │
      ├── 字段：设计流量 = 4.5
      ├── 字段：建成年月 = 1996-08
      └── 字段：结构形式 = 钢筋混凝土
```

### 14.1 原则

V0.1 不为每一种调查表建立一张完全独立的数据表。

采用：

```text
调查记录
+
字段定义
+
字段值
```

这种方式保存动态调查字段。

主要目的是支持：

- 29 类调查表；
- 后续表格版本变化；
- 字段增加或删除；
- 不修改数据库主结构即可扩展调查表。

---

## 15. InspectionResult：评价结果

保存附表2中每个评价项目的实际调查结果。

例如：

```text
工程：1号节制闸

结构破损
└── 闸室
    ├── 评价等级：C
    └── 情况描述：东侧边墙发现贯穿性裂缝……
```

### 15.1 主要属性

建议包括：

- 内部 ID
- SurveyRecord ID
- InspectionItemDefinition ID
- 评价等级
- 情况描述
- 备注
- 修改时间

### 15.2 重要原则

系统必须区分：

```text
评价标准
```

和：

```text
现场情况描述
```

评价标准来自调查表定义。

现场情况描述由调查人员根据真实调查结果填写。

二者不得混为同一个字段。

## 16. 最终工程状况类别

SurveyRecord 中预留：

```text
overall_grade
```

第一版允许：

```text
NULL / 未确定
A
B
C
D
```

V0.1 不自动综合判级。

以后单独建立：

```text
grading service
```

根据甲方最终规则计算或辅助判断。

综合判级逻辑不得写死在：

- UI；
- SQLite 表；
- Excel 导出程序。

## 17. 业务编号

业务编号与数据库内部 ID 完全分开。

示例：

```text
数据库 ID：
84217

业务编号：
1-01-01-02-037
```

数据库 ID：

- 系统内部使用；
- 永久稳定；
- 用户通常不可见。

业务编号：

- 面向实际调查业务；
- 可以自动生成；
- 可以查询；
- 未来规则允许调整。

-

## 19. 编号规则变化

工程对象中建议同时保存：

```text
business_code
code_scheme_version
```

未来如果编号规则发生变化：

- 旧编号继续保留；
- 新工程使用新规则；
- 不修改数据库内部 ID；
- 不因为业务编号变化破坏历史调查关系。

## 20. 数据继承原则

下一次调查时，部分字段可能沿用上一次调查结果。

系统采用：

```text
复制值
```

而不是：

```text
引用旧值
```

例如：

```text
2026设计流量 = 4.5

新建2027调查：
复制 → 2027设计流量 = 4.5
```

此后如果2027调查发现：

```text
设计流量应修改为4.8
```

只修改2027记录。

2026仍保持：

```text
4.5
```

从而保证历史数据可追溯。

---

## 21. 附表1中的复杂表格

附表1中存在：

- 普通单值字段；
- 多年份字段；
- 作物分类矩阵；
- 多种水源分类；
- 多行工程数据；
- 规划数据。

因此附表1不能简单理解为传统的一行数据。

V0.1 暂不一次实现全部附表1。

在后续进行附表1数据字典设计时，
根据实际表格结构增加“重复行 / 矩阵型字段”的支持。

当前数据模型应预留该能力，
但 V0.1 暂不实现复杂通用表格设计器。

## 22. 图片与附件

V0.1 暂不实现照片管理。

未来如启用：

```text
Attachment
```

应作为独立数据实体。

数据库只保存：

- 文件路径；
- 所属调查记录；
- 所属检查项目；
- 文件类型；
- 拍摄时间；
- 说明等。

图片和视频文件本身原则上不直接存入 SQLite。

## 24. Excel 与数据库关系

系统数据流：

```text
纸质调查表
      ↓
PySide6录入界面
      ↓
SQLite
      ↓
查询 / 修改 / 统计
      ↓
Excel输出
```

Excel 不作为 SQLite 的替代数据库。

同时保留未来：

```text
Excel批量导入
```

和：

```text
全数据库Excel导出
```

能力。

## 27. 不可违反的数据规则

系统后续开发必须遵守：

1. 历史调查记录不得被新批次覆盖；
2. 工程对象与调查记录必须分离；
3. 数据库内部 ID 与业务编号必须分离；
4. 已使用的调查表版本不得直接覆盖修改；
5. 评价标准与现场情况描述必须分离；
6. 综合 a/b/c/d 判级算法必须独立；
7. Excel 只是输入输出接口，不作为核心数据库；
8. 真实调查数据不得写入程序代码或 Git 仓库；
9. 新批次继承历史数据时必须复制，而不是共享同一值；
10. 当前不确定的业务规则优先预留，不提前写死。
